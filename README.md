# WipeOS

A minimal Linux image for verifiable memory wipes. On each host in a pod, WipeOS overwrites the agreed erasure target with challenge-dependent data and answers a challenge server's queries, so that at most R bits of uncommitted state survive. It builds on Amodo's PoSE memory-wiping work and the Pod-PoComp protocol.

## Running wipeOS

Current as of Oct 26, 2026. Update this section whenever the configuration changes.

**Where things run (D38).** Builds and boots run on x86_64 Linux build hosts: the cluster, or any x86_64 Linux machine. My laptop (Windows on Arm, WSL2) is a workstation for editing, Claude Code, lint, git and SSH, and doesn't build or boot (D40). CI runs lint, the self-tests and the index check on every pull request to `main` and every push to `main` (D43). When a change touches what goes into the image or how it boots, CI also builds the image and boots it four times, under KVM and TCG (D46–D49).

### On a build host

**Launch the current image.** From the repo, run `scripts/run.sh`. It rebuilds the stub and the image, boots WipeOS in QEMU, and exits with the result.

| Command | What it does |
| --- | --- |
| `scripts/run.sh` | Prod mode, 1 GiB, 4 KB pages: boot, print the report, power off |
| `scripts/run.sh --mem 3` | 1 GB huge pages (D22): reserves N−2 = 1 page |
| `scripts/run.sh --mem 4 --pages 4k` | Ordinary 4 KB pages at any size, for measuring bookkeeping cost |
| `scripts/run.sh --mode dev` | After the report, a shell on the console; `exit` powers the VM off |
| `scripts/run.sh --test-fail` | Negative test: a failing check, exit 1 |
| `scripts/run.sh --no-build` | Boot the existing image without rebuilding |
| `scripts/run.sh --accel tcg` | Software emulation even where KVM is available |

`scripts/run.sh --help` lists every option. In dev mode, **Ctrl-A** then **X** quits QEMU directly, which counts as an unclean end (exit 2).

**Accelerator (D39).** KVM runs the guest directly on the host's CPU; TCG, QEMU's software emulation, translates every guest instruction and is far slower. With `--accel auto` (the default), `run.sh` uses KVM when the host is x86_64 and `/dev/kvm` is readable and writable by you, and TCG otherwise. `--accel kvm` exits 2 before building if KVM isn't usable, and `--accel tcg` always emulates.

**Exit codes (D30).** 0: the stub reported `RESULT=SUCCESS` and the VM powered off cleanly. 1: `RESULT=FAIL`, then a clean power-off. 2: anything else (build failure, kernel panic, timeout, no RESULT line, no clean power-off, or `--accel kvm` without KVM). 3: bad arguments.

**Logs.** Each run writes `logs/run-<date>-<time>.log` (gitignored), and the build output goes to the matching `-build.log`. A boot log starts with `RUN` lines (QEMU version, git commit, options including `accel=`, and the exact QEMU command, D23), followed by the serial console: kernel messages and the stub's report.

**The report (D29).** The stub, `/sbin/wipeos-init`, runs as process 1 (D25) and prints only `WIPEOS key=value` lines: `BEGIN` with the git commit, the mode, memory (`mem.*`), the RAM ranges and the kernel's own sections (`iomem.*`, including `iomem.kernel_total_bytes`), the unpacked initramfs (`initramfs.shmem_kb`), huge pages (`hugetlb.*`), address randomization (`aslr.*`), PCI devices (`pci.*`), one `check.*` line per check, and finally `RESULT`.

**Huge pages.** With `--pages auto` (the default), up to 2 GiB uses 4 KB pages. From 3 GiB, `run.sh` reserves N−2 pages of 1 GB at boot and adds `-cpu max`, because QEMU's default CPU model doesn't advertise 1 GB page support. The first gigabyte is always broken up (BIOS areas, the legacy hole, the kernel) and the top of guest RAM has a reserved region, so N−2 is the safe count. Huge pages become the default once the fill code lands (D22); the 4 KB runs stay as a comparison.

**Booting by hand.** From `~/wipeOS/buildroot`, this is what `run.sh` runs for a 1 GiB prod boot on a host with KVM (use `-accel tcg` without it):

```bash
qemu-system-x86_64 -accel kvm -m 1G -vga none -nographic -no-reboot -kernel output/images/bzImage -append "console=ttyS0 panic=-1 wipeos.mode=prod"
```

Adding `rdinit=/bin/sh` to `-append` bypasses the stub and gives a rescue shell, with nothing mounted.

**Rebuild after a change** (from `~/wipeOS/buildroot`):

- After changing the stub in `src/stub/`: `scripts/run.sh` rebuilds it, or run `make wipeos-stub-rebuild && make`.
- After changing the kernel config with `make linux-menuconfig`: `make linux-rebuild && make`
- After changing Buildroot settings with `make menuconfig`: `make`. Removing a package or changing the init system needs a full rebuild, `make clean all` (about 40 min).
- Save both configs afterwards. Buildroot remembers where our defconfig lives (D31):

```bash
make linux-update-defconfig
make savedefconfig
```

### Checks that run anywhere

These run on the laptop, on a build host and in CI:

- `scripts/lint.sh` lints all C under `src/` with checkpatch, gcc's warnings and analyzer, and cppcheck (D33). It always compiles for x86_64 (D42) and prints its tool versions first. `scripts/lint-selftest.sh` checks that each lint check catches a planted defect, and that the pre-commit hook allows or refuses commits as it should.
- `scripts/hooks-selftest.sh` feeds each Claude Code hook in `.claude/hooks/` the input Claude Code would send, for a fixed table of cases, and exits 0 only if every one gives the expected result: block, ask or pass (D37). Add `-v` to list every case.
- `scripts/context_index.py --check` exits 1 if `context/INDEX.md` is out of date.

### How changes reach main (D44)

Work happens on a branch, `claude/<topic>` for agents, which is pushed and opened as a pull request to `main` (`gh pr create`). CI must pass, and only I merge. A ruleset on `main` requires a pull request and the CI checks and blocks force pushes; `.claude/hooks/guard-git.py` stops agents from pushing to `main`, merging or approving.

### Build and boot in CI (D46–D49)

The **`build and boot`** check builds the image on a GitHub-hosted runner and boots it with `scripts/run.sh` four times: `--accel kvm`, `--accel tcg`, `--test-fail` (expects exit 1) and `--mem 4`. `scripts/ci-changes.sh` decides first whether anything that can change the image or the boot changed (`src/`, `package/`, `configs/`, the external-tree files, `run.sh`, the script itself, or the workflow). If not, the check passes in seconds and its summary says so. The run's summary page shows the build time, the `bzImage` size and the boot table, and the run keeps two artifacts for 14 days: `boot-logs` (the four boot logs and the last 200 lines of the build log) and `bzImage`.

**Booting an image built by CI.** On a build host with `gh` installed and logged in (`gh auth login`), fetch the image from a run instead of building it:

```bash
cd ~/wipeOS
gh run list --workflow CI --branch main --limit 5
mkdir -p buildroot/output/images
rm -f buildroot/output/images/bzImage
gh run download <run-id> -n bzImage -D buildroot/output/images
scripts/run.sh --no-build
gh run download <run-id> -n boot-logs -D logs/ci-<run-id>
```

`gh run download -n <name>` fetches one artifact by name, and `-D` says where to unpack it. It refuses to overwrite a file that already exists, hence the `rm -f`; the next `make` rebuilds the image anyway. The last command fetches the CI boot logs to compare with your own.

### Set up on a new machine

The repo is a Buildroot external tree named `WIPEOS` (D31). Buildroot itself is not committed (it is in `.gitignore`); each build host clones it. Keep the repo off Windows filesystems and out of paths with spaces.

**Workstation (laptop).** Ubuntu 26.04 under WSL2, so the lint tools are the same releases as CI's (D42). Lint needs the x86_64 cross compiler, cppcheck, perl and curl:

```bash
git clone git@github.com:ztblick/wipeOS.git ~/wipeOS
cd ~/wipeOS
git config core.hooksPath .githooks
sudo apt install gcc-x86-64-linux-gnu libc6-dev-amd64-cross cppcheck perl python3 curl
scripts/fetch-checkpatch.sh
scripts/lint.sh && scripts/lint-selftest.sh && scripts/hooks-selftest.sh
gh auth login
```

`git config core.hooksPath .githooks` turns on the pre-commit lint, which git never enables from a clone by itself. `scripts/fetch-checkpatch.sh` downloads the kernel's `checkpatch.pl` for our pinned kernel version into `.cache/` (D41); run it again after the kernel version changes.

**WSL notes.** Windows paths are kept out of the Linux PATH (`appendWindowsPath = false` in `/etc/wsl.conf`), because Buildroot fails on paths with spaces. VS Code still opens with `code .` through an alias in `~/.bashrc`.

**Build host (cluster or any x86_64 Linux).** What the host needs:

- **Buildroot's host packages** (the "System requirements" chapter of the Buildroot manual), and `qemu-system-x86_64` under that name for `run.sh` (D23). On Debian or Ubuntu, this covers them (`libncurses-dev` is only for `make menuconfig`):

  ```bash
  sudo apt install build-essential bc bzip2 cpio diffutils file findutils gzip patch perl python3 rsync sed tar unzip wget git libncurses-dev qemu-system-x86
  ```

- **Internet access** for the first build: Buildroot downloads about 1.2 GB of sources (the kernel, GNU toolchain and packages) into `buildroot/dl/`, and checks each against its hash.
- **Disk:** about 11 GB for `buildroot/output/` and `buildroot/dl/`.
- **KVM** (optional, for fast boots, D39): your user needs read-write access to `/dev/kvm`, usually through the `kvm` group. `[ -r /dev/kvm ] && [ -w /dev/kvm ] && echo KVM usable` checks it. If `grep -cw vmx /proc/cpuinfo` prints 0, virtualization is off in the firmware, and only an admin can turn it on. Without KVM, `run.sh` falls back to software emulation, which still boots the 1 GiB image in about 2 seconds on the cluster.

**QEMU without root.** If you can't run `apt install` (no `sudo`) on an Ubuntu host, unpack Ubuntu's own QEMU packages into your home directory and put a wrapper named `qemu-system-x86_64` on your `PATH`. It is still the distribution's QEMU (D23), and `run.sh` needs no change:

```bash
mkdir -p ~/opt/debs && cd ~/opt/debs
apt-get download qemu-system-x86 qemu-system-common qemu-system-data seabios ipxe-qemu libfdt1 liburing2
for f in *.deb; do dpkg -x "$f" ~/opt/qemu; done
mkdir -p ~/opt/bin
cat > ~/opt/bin/qemu-system-x86_64 <<'EOF'
#!/bin/sh
Q=$HOME/opt/qemu
export LD_LIBRARY_PATH=$Q/usr/lib/x86_64-linux-gnu${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}
export QEMU_MODULE_DIR=$Q/usr/lib/x86_64-linux-gnu/qemu
exec "$Q/usr/bin/qemu-system-x86_64" -L "$Q/usr/share/qemu" -L "$Q/usr/share/seabios" -L "$Q/usr/lib/ipxe/qemu" "$@"
EOF
chmod +x ~/opt/bin/qemu-system-x86_64
echo 'export PATH=$HOME/opt/bin:$PATH' >> ~/.bashrc
```

`apt-get download` and `dpkg -x` fetch and unpack packages without installing them, so they need no root. The wrapper points QEMU at the unpacked libraries, its modules (Ubuntu builds TCG as a loadable module) and its firmware directories (`-L`: the BIOS and the network card's boot ROM), which it would otherwise look for under `/usr`. `libfdt1` and `liburing2` were the only libraries the cluster lacked; on another host, `LD_LIBRARY_PATH=~/opt/qemu/usr/lib/x86_64-linux-gnu ldd ~/opt/qemu/usr/bin/qemu-system-x86_64 | grep 'not found'` lists any others to download the same way.

The repo is public, so a build host can clone it over HTTPS without a GitHub key. Buildroot must be exactly the tag in `configs/buildroot.version`, which CI reads too (D47): the defconfig takes the kernel's hash from that tag's `board/qemu/patches`.

```bash
git clone https://github.com/ztblick/wipeOS.git ~/wipeOS
cd ~/wipeOS
git clone --branch "$(cat configs/buildroot.version)" https://gitlab.com/buildroot.org/buildroot.git buildroot
cd buildroot
make BR2_EXTERNAL=.. wipeOS_x86_64_defconfig
make
cd .. && scripts/run.sh --no-build
```

The first `make` builds the toolchain, kernel, stub and initramfs; the image lands in `buildroot/output/images/bzImage`. On the laptop's 8 cores it took about 40 minutes; Buildroot uses every core, so a larger server is faster. Config files refer to the repo as `$(BR2_EXTERNAL_WIPEOS_PATH)`, so it can live anywhere. The `RUN` line of the boot log should show `accel=kvm` if KVM is usable.

To commit from a build host, also run `git config core.hooksPath .githooks`, install cppcheck 2.11 or later, and run `scripts/fetch-checkpatch.sh`. The pre-commit lint then runs with the host's own gcc and cppcheck, and it refuses a commit if a tool is missing.
